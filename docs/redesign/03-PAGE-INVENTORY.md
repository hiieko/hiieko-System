# HIIEKO Web + Mobile Redesign — Page Inventory

**Basis:** current `web/src/app` route files, `route-roles.ts`, navigation, API client, feature modules, and the prior consolidated route inventory. Source is inspected in a dirty checkout; re-check affected files before implementation. Route presence is not a claim of runtime quality or business-policy approval.

## Shared acceptance baseline

Every in-scope web route and mobile screen must retain its current route/screen, role restrictions, organization/project scope, API-backed actions, authentication behavior, and persistence. Review real loading/populated/empty/no-results/error/denied/saving/success states where applicable. For web, check 390/768/1280/1440 px; for Mobile, use device/platform-specific sizes and interaction conventions established by the Mobile audit. Check keyboard/focus or native accessibility, contrast, status text, and touch controls. Use existing feature/shared components where appropriate. Page-specific criteria below supplement—not replace—[05-REVIEW-AND-QA.md](./05-REVIEW-AND-QA.md).

## Production mobile application

Mobile is in scope, but no screen/route inventory is asserted here because the Mobile source has not yet been audited for this redesign. Do not copy the web route list or wireframes into Mobile.

The separate mobile audit task must inventory existing screens/navigation by role, purpose and workflow; identify current components, API clients, persisted/offline queues, localization, device affordances, and test coverage. At minimum, trace which existing screens support the real field-day workflows (assigned tasks/progress, attendance, daily reports, photos, notifications, and any other confirmed flows). Record actual screen identifiers from source—do not invent them.

For each confirmed mobile screen, create an inventory row containing: source screen/entry; purpose and user roles; API and persistence/offline dependencies; required improvement; existing behavior that must remain; device/accessibility/responsive criteria; relevant test; acceptance evidence. Apply the approved visual anchors and semantic tokens where suitable, but let native navigation, field capture, keyboard, safe-area, offline/sync and touch requirements determine layout.

Mobile implementation is a separate roadmap sequence: audit → mobile-specific design brief → owner review of the bounded mobile prototype brief → implement one existing mobile workflow → owner review → expand in independently verified screen families. It does not authorize Mobile changes in the web `/tasks` prototype task.

## Dependency notes

- Shared shell/token work affects many routes; implement only after the first page prototype is accepted and make it independently reviewable.
- Root `/` and `/control-tower` share `ControlTowerSurface`; do not duplicate or fork their UI.
- `/qa-qc` is an alias, not a second page family. `/rapoarte/form` delegates to the existing report form.
- Project context and route roles are cross-cutting dependencies. Any discovered contract drift is a blocker, not a redesign decision.
- The document route depends on actual storage/provider behavior and server-side authorization. No storage architecture decision is made by this inventory.
